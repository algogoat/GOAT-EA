# Recovering an interrupted legacy monitor startup

MT5 LiveUpdate can replace a monitor process and lose its original CPU job.
That does not permit adopting the replacement process, inventing stable
allocation evidence, rerunning startup, or discarding the original worker claim.

The controller provides a deliberately narrow migration route for a retained,
scoped passive monitor bootstrap. It preserves startup issuance, historical
attempts, editor drafts, queue history and the separate running peer.

## Commands

Use the public installed `goat.exe studio --installation <receipt>` prefix, or
the same `goat_studio.py --installation <receipt>` source entrypoint during
explicit development qualification. Customer shipping still requires a matched
reviewed bundle; using source is not proof of an installed customer update.

1. `peer-prepare --terminal-executable <other MT5> --data-root <its data root>`
   prepares exact process/path protection. `peer-apply --review-id <id>
   --confirm-reviewed` applies the reviewed policy within the user's existing
   setup scope. It grants no control over the peer. Unknown/replaced peers block.
2. `bootstrap-retirement-prepare --specification <original specification.json>
   --bootstrap-receipts <original receipt directory>` inspects original issuance,
   registered claim/slot, dead original host/process, idle connected demo monitor,
   Algo-off state, retained controls, queues, fixed tasks and human/agent inboxes.
3. `bootstrap-retirement-apply --review-id <id>` normally closes only the exact
   reviewed replacement monitor, once. It proves process absence before releasing
   the original claim and startup slot in one registry transaction. A retry of
   this ID inspects the outcome; it never sends another close or starts anything.
4. After successful retirement, `switch-plan` prepares the actual session
   migration. Existing user confirmation for that exact switch remains required.
   The switch checks registered retirement evidence, preserves research and
   revokes old control. A fresh session still needs legitimate Give to Agent.

## Evidence and limits

- A pending retirement fences ordinary setup, switching and research commands.
  Its exact ID survives failure. `close_outcome_unresolved` is not a successful
  close: MT5 may require human handling. Do not force-kill or repeat the effect.
- The old scoped worker completion schema has a dedicated read-only validator.
  It verifies request consumption, frozen package, exact database completion,
  restored transaction and registry release. A settled historical attempt never
  proves the current worker claim is clear. Evidence is retained, not deleted.
- R17's observation revision is an editor baseline while unsaved edits exist.
  This route accepts that explicit legacy case only with the exact current
  controller status, unchanged generation/owner and a matching durable editor
  draft, which is copied into the review. Unknown/stale formats still block.
- Permanent MetaTester Windows services may remain. They must have an exact
  Windows service registration and services.exe parent; the selected terminal
  must have no active loopback service connection. Unidentified tester processes,
  updaters, selected research attempts and uncertain observations block retirement.
  No service is stopped or adopted.
- Native orphan continuation flags are not modified here. Clearing an actual
  orphan requires the separate V1.49 reviewed native action and real readback.
  Internal build admission, compatible catalog/setup, pairing and permissions
  remain separate from receipt retirement.

Host tests cover crash/retry, changed identity, pending work, editor preservation,
atomic registry rollback, shared guards and old completion validation. Native
qualification has established peer protection, actual retirement after the user's
normal close, and user-confirmed parking of both historical sessions. A fresh
session was bootstrapped using the compatible installed V1.48 EA. MT5's updater
then discarded the requested monitor profile; recovery is tracked as CTRL-010.
No fresh optimization start or complete end-to-end qualification is claimed.

## Installing a reviewed pair after parking

The authenticated desktop installer must verify internal build admission and the
exact bundled EA, controller and compatible catalog before replacing an existing
installation. These trusted local commands provide serialization, not admission:

- `switch-verify-park --review-id <id>` verifies a completed PARK, immutable
  research archives, unchanged external databases and a stopped selected terminal.
- `switch-replace-receipt --review-id <id> --candidate-receipt <path>
  --expected-sha256 <old raw receipt hash>` replaces only the registered receipt
  under the controller session lock and external database write locks. Stage the
  candidate outside the active controller and terminal state directories. The
  physical terminal/data/common/state roots must match the archived installation.

The replacement retains its candidate and publication intent in the PARK archive.
Retry the same candidate/review/hash after an uncertain response; never remove its
EA payload while publication is unresolved. A successful response is
`receipt_replaced` with the candidate's raw `receipt_sha256`. It creates no session,
grants no agent control and launches nothing. Ten host tests cover artifact and
receipt changes, database/session races, invalid journals and interrupted receipt
publication. Native installation through this route remains unqualified.
